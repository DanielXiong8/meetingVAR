# 音频时间轴修复与验证

## 修复目标

处理实时转写反复出现“PCM时间戳不连续，正在重连并重新锚定媒体时间”的本地原因。本轮只修改引擎与回归测试，不打包源码或安装器，不修改UI，不调用讯飞或真实音频设备。

## 已复现的问题

- 双源混音按请求游标起点生成PCM，却返回另一音频起点；首次读取可凭空增加约一秒前置数据，后续游标推进错位。
- 单源只选择起点晚于游标的整块，跨游标的有效尾段被直接跳过。
- 在真实Unix时间量级上逐次累加0.1秒，会在约33秒后累计超过RTASR半采样容差；这不是网络错误。
- 初次修复的停机路径若直接取两路最大结束位置，会越过一路断流后的后续连续段；独立复核已补足并修复。

## 当前实现

- `capture/audio.py`：采集时间使用固定原点加整数采样计数，实际重采样输出长度决定时间；读取跨界时裁取有效采样。
- 单源读取返回下一段连续音频，真实缺口仍保留，不把不连续段直接拼接压缩时间。
- 双源混音采用统一采样网格，PCM第一个采样与返回时间一致。正常读取以较慢一路的可用结束位置为边界，快路尾段留在原缓冲中等待。
- 某路持续0.35秒无新数据时明确提示并使用剩余来源，缺失区域以静音表示；恢复后继续对齐。该机制不能恢复驱动已丢失的声音。
- 驱动读错误/溢出会显式提示，重置重采样状态并重新锚定实际时间，不伪造连续录音。
- `live.py`：停止采集后循环排空多个连续段；双源停机也按最短可用段推进，避免越过后段音频。
- RTASR的半采样阈值保持不变：修复上游时间轴，不通过隐藏提示或放宽阈值掩盖问题。

## 验证

1. 修复前，三个最小合成用例均失败：双源起点不一致、跨界尾段丢失、错相双源样本不一致；修复后通过。
2. 90分钟虚拟双源输入：两路100ms音频错开20ms到达，经过实际AudioCapture缓冲读取、DualCapture混音和RTASR发送代码，全部输出与独立构造的预期PCM哈希一致；同一连接结束一次，无假重连。测试使用虚拟时钟加速，不是90分钟真实会议。
3. 独立RTASR长时测试：54000个输入块、135000帧连续发送；真实±2采样缺口/重叠仍触发分界。
4. 覆盖慢路等待、持续缺路/恢复、重采样输出长度、单路备用、断流后停机排空、模拟驱动溢出和字幕定稿等边界。
5. Python3.10带依赖环境中96项相关回归通过，新增模拟驱动溢出单项另通过；最终最小依赖套件发现398项，357项通过、41项按依赖跳过，编译检查通过。

## 生效与边界

本机已安装桌面壳调用的引擎指向当前源码副本，下一次开始会议会载入修复，不必为这两个引擎文件重新打包UI。当前未发现活动会议引擎，本轮未停止或重启用户服务。

这是截图对应本地时间轴缺陷的代码修复和自动化验证，不是对讯飞识别准确率、真实设备时钟漂移、回声消除或长会硬件稳定性的认证。仍需真实设备短会确认；按用户要求，本轮没有生成或更新源码ZIP、安装包或提交材料。
