## 2026-10-10（续）· HD 补录产品决策落地：临时 5GB/场 + 最终产物 MB 级

**来源**：用户对验收报告中的 HD 资源风险（90s@1440p 约 33GB 临时帧）给出硬约束——
"顶多 5G 临时文件/每场，最后生成的厚薄纪要应该是 MB 级"，并选择推荐方案
（降到实测可达帧率 + 双线性缩到 1280 宽）。

### 落地内容（`src/meetingvar/capture/hd.py` + `config.py`）

| 项 | 实现 | 实测/验证 |
|---|---|---|
| 缩放 | 帧双线性缩到 `HD_WIDTH=1280` 宽（窄屏不放大；宽高取偶适配 yuv420p） | 2560×1600→1280×800：帧 3.07MB（原 12.3MB，↓4×） |
| 每场临时预算 | `HD_TEMP_BUDGET_BYTES=5GiB`（env `MEETINGVAR_HD_TEMP_GB`）；**同一 HDCapture 实例跨多次命中共享**（=一场会议） | 逐帧硬上限：累计 ≤ 预算（不超 1 字节） |
| 帧率编排 | 目标帧率 = 剩余预算/帧尺寸/补录时长，标称 30fps 仅为上限；触底 `FPS_FLOOR=1.0` 后由硬上限截断 | 20 帧/4s → 5fps 且仍覆盖 4s（时长不缩水）；第 2 次命中 5fps < 第 1 次 10fps |
| 预算用尽 | 放不下 1 帧 → 跳过补录（不留空目录）+ 提示；回溯音频+截屏照常 | 单测断言无新目录、`_skipped_for_budget` |
| 诚实标注 | `meta.json` 记录 fps_nominal/planned/actual、帧数、预算用量、budget_hit；完成语打印 mp4 MB 与累计用量 | HD 11 例全绿（含 ffprobe 与管线接线） |

**真实屏幕实测（本机 2560×1600，5s 缩样 + 5GiB 预算）**：缩放后 1280×800、达成 13.2fps
（瓶颈 = mss 抓屏 ~51ms + PIL 缩放 ~25ms），90s 帧量 ≤5GiB（构造保证）；
**mp4 ≈0.019MB/s → 90s 静态桌面 ≈1.7MB（MB 级 ✓）**。标称 30fps 在本机不可达——
帧率改为"尽力值"，实测值落 meta 并用于合成（视频时长始终 ≈ 真实时长）。

### 代价与残余（写明，不粉饰）

1. **分辨率**：1280 宽对 1440p 屏是 0.5× 降采样——UI 文字仍可读，但细节（小字号代码）
   损失需真实会议内容确认（产品取舍，用户已拍板）；
2. **帧率**：实测 13fps（本机），平滑度低于 30fps 叙事——路演/BP 中"30fps 补录"表述应改为
   "高帧率补录（实测可达 ~13–20fps，视机型）"；
3. 动态内容（视频/翻页）下 mp4 体积上界未实测（1.7MB/90s 是最低端估计）；真实 90s 长跑未做。

### 主动待办（因本次改动而变化）

- BP/PPT 中的"30fps 高清补录"话术需同步为"可配置帧率补录 + 临时空间封顶 5GB/场"
  （**未改，等用户确认后一并改 BP/PPT**，避免擅自改答辩材料）。

## 2026-10-11 · test1 真实会议三组对照实测（3h49m，英中双语）

**设置**：真实组会录音 13770s。meetingVAR 跑三遍，唯一变量 = 词表：
对照（无词表）/ A（人工 8 词）/ B（meetingVAR 读杨坤鑫代码仓库自动抽词，全漏斗 1044 词）。
新增 `meetingvar transcribe` 转写模式（显式导出 txt；零落盘默认不变）。

**因这次实测而修的三个真缺陷**（均已提交、带回归测试）：
1. `llm_extract` 把全部 md/txt 拼进 prompt（本仓库 120KB ≈ 数万 token）→ llama_cpp 4k 上下文直接 HTTP 400。
   加单文件 6000 字/总量 40000 字预算（服务侧另开 --n_ctx 32768）。
2. 同一转写块命中 N 个词各存一份 300s 片段：1044 词表下 33% 进度 752 片段/6.9GB，
   **C 盘只剩 6.5GB 时紧急中止**。改为每次回看一个片段、evidence 记全部命中词（重跑后 428 片段/4.1GB）。
3. 对照组（无命中）按零落盘连转写都不写——测试需要显式导出，催生 transcribe 命令（用户拍板）。

**核心发现（本测试最大价值）**：

| 组 | 词表 | 纠错数 | 与对照不同行数(共1548) | 结论 |
|---|---|---|---|---|
| A | 人工 8 词 | 16 | **14** | ✅ 精准：figure←four/fair/future；机器学习←基因学习/己学习；随机森林←随习森林 |
| B | 全漏斗 1044 词 | **7457** | **493** | ❌ 灾难：英文自我介绍被改写成词沙拉（"corresponding author is professor"→"correspondmaing frameworks APIs repository thinking"）；改写链 This→think→thinking、images→messages→usage；中文"不同区域"→"不限定区域"×10 |

**结论**：漏斗产出**不经治理直接喂纠错层 = 转写被改坏**。根因三层：
(a) 漏斗无"口说价值"过滤——代码符号、常见英文词（user/query/framework）、笔记短语（不限定区域）全部入表；
(b) 拉丁纠错规则（difflib≥0.6）没有稀有度/上下文守卫，常见词互相改写并级联；
(c) 词表没有分层——L1 监听可以"宽进"（多触发无伤大雅），但改写转写文本的纠错必须"严进"。

**下一轮建议（未实施，待定案）**：
1. **词表分层**：监听表（宽，全漏斗产出）≠ 纠错表（严，只留术语级）；
2. 漏斗加"口说价值"守卫：语料高频常用词/纯代码标识符/带标点短语不入表；LLM 提示词加
   "只要会被口头说出的术语与实体"约束；
