# 0.2.2 全库理解冷启动修复记录

日期：2026-10-19。触发场景：把项目切到 `D:\项目\数据结构`，清空派生缓存后点“全库理解”，第 1 块即失败：“模型返回的 JSON 或结果结构无效”。

## 根因

1. 本地 4B 模型偶尔在完整 JSON 末尾多输出一个引号（`...}]}"`）。
2. 更常见的是把原文中的英文双引号直接塞进 JSON 字符串（例如 `"paperless"`），没有转义，解析器在第 1300 字符处报 `Expecting ',' delimiter`。
3. 学生报告类密集合块会让模型输出顶到 8192 token，`finish_reason=length`，旧逻辑把它当成非法 JSON 并直接中断整次 16 块阅读。
4. 重试时在提示词末尾追加说明，会把已经卡满输入预算的块顶成 `context_budget`。

## 修复

- `_stable_json` 容忍“完整对象后仅多一个引号”的单一伪影；仍要求通过严格 schema 校验。
- 新增 `_repair_inner_quotes`：只在严格解析失败后，把字符串内部未转义的英文引号转义；修复结果仍须通过 schema 与原文证据校验。
- 单块最多 3 次尝试：首次 0.2，之后 0.0；重试提示仅在预算仍可容纳时追加。
- 正常模式仍失败时改用“只提最多 5 个关键词”的精简模式重读该块（persons/events 为空），避免密集合块因输出过长拖垮全库。
- 仍失败的可恢复块（invalid_json / truncated / context_budget 等）跳过并继续；认证、配额、模型不存在等不可恢复错误仍立即停止。
- 结果新增 `failed_chunks`；部分完成返回 `partial_read`，UI 显示覆盖率与失败块，并允许勾选已读候选词；只有 `ok && complete` 才发布 `interest_context.json`。

## 验证

- 单元测试：尾部引号、未转义内层引号、非法 JSON 重试、精简模式降级、部分完成继续、认证错误立即停止。
- CLI 冷启动（清空项目 understand 缓存后，本地 Qwen3-4B 16K）：16/16 块、覆盖率 100.0%；第 13 块（学生报告 5763 字）触发精简模式，其余块正常；发布 `interest_context.json`，概览“数据结构与算法实验项目资料集合。”
- 0.2.2 安装包真实 UI 冷启动：再次清空项目缓存，项目页预算显示 60156 字 / 14 块；读完 **14/14 块、100%**，界面显示候选词，`interest_context.json` 已写入，`ui.log` 记录 `ok=True`。
- 同一项目此前表现：第 1 块即失败；修复迭代中先后出现第 5、13 块失败，最终收敛到全部块完成。

## 边界

- 精简模式只提关键词，不提取人名/事件；该块的事件覆盖弱于正常模式。
- 全库理解的质量仍取决于本地模型，候选词需要用户勾选后才写入词表。
- 本次清空的是派生缓存与测试产物；会议证据 `data/pool`、`data/clips`、`data/reports`、确认词、说话人名册和配置密钥均保留。
